# B 站扫码登录

凭证失效时的标准处理流程。**默认动作就是登录**，不要绕：不要去读用户浏览器、不要索取 Cookie、
不要试图用别的账号。

## 流程

1. **先确认是否需要登录。** 调 `bili_login_status`：
   - 返回 `already_logged_in` ⇒ 已经好了，别再折腾；
   - 返回 `no_active_login` ⇒ 继续下一步。
2. **发起登录。** 调 `bili_login_start`：
   - 二维码会渲染成 PNG，默认存到 `downloads/`（`bili-login-qr-<时间戳>.png`）；
   - 返回里带 `qrPath`（绝对路径）和有效期（约 180 秒）。
3. **把路径告诉用户**，并明确两件事：
   - 请用手机 **B站 App** 扫码，并在手机上点确认；
   - 确认时选「**记住我 / 长期**」（选 24 小时的话第二天就得重来）。
   如果对话支持发图片，可以直接把那个 PNG 展示出来；**不要把图片内容转成文字描述**。
4. **轮询结果。** 反复调 `bili_login_status`（间隔几秒）：
   - `pending` / `scanned` ⇒ 继续等，别催；
   - `confirmed` ⇒ 成功，凭证已写入，**二维码图片已自动删除**，如实告知用户；
   - `expired` ⇒ 二维码失效（图片也已清理），重新调一次 `bili_login_start` 再来。
5. **不要自己验证凭证**：登录成功后若要确认，用 MCP 服务器的 `check_bilibili_credentials`
   （它返回 `configured` / `logged_in`，且永远不会返回 Cookie 值）。

## 红线

- **不索取 Cookie。** 不要要求用户把 SESSDATA / bili_jct / DedeUserID 贴到对话里，也不要读浏览器存储。
- **不显示凭证内容。** 即使拿到了，也不要打印或复述。
- **不擅自换账号。** `bili_login_start` 默认在已登录时不会重新发起；只有用户明确要求换号才传 `force: true`。
- **不留二维码残骸。** 登录成功或失效后二维码都应被删除；如果发现目录里还留着旧图，提醒用户可清理。
- **不重复轰炸。** 用户没扫码就等着，不要连发多次 `bili_login_start` 把目录塞满。

## 常见情况

| 现象 | 处理 |
|---|---|
| 用户在手机上看不到确认页 | 让他在 App 里「我的 → 扫一扫」重试；仍不行就重新生成二维码 |
| `expired` 反复出现 | 说明用户没及时扫，重新生成即可，不算故障 |
| 登录成功但读取仍报未登录 | 让 MCP 服务器重新连接（重启 Pi 或 `/mcp-adapter reconnect`）后再试 |
| 用户问「能不能不用扫码」 | 当前只提供扫码方式；不要引导用户手工填 Cookie |
